## 一、完整链路概览

### 1.1 技能安装链路

```
用户操作（AgentModal 弹窗 → 勾选技能）
  ↓
_collectAndSave() → data.skills = ['web-search', 'zhihu-search']
  ↓
Api.createAgent(data) → POST /api/agents
  或 Api.updateAgent(agentId, data) → PUT /api/agents/:id + PUT /api/agents/:id/agents-md + PUT /api/agents/:id/tools-md
  ↓
后端 agent-routes.js
  ├─ createAgent(): 写入 openclaw.json → rosterSync.syncAllRosters()
  或 updateAgent(): 更新 openclaw.json → rosterSync.syncAllRosters()
  ↓
rosterSync.syncAllRosters()
  ├─ _validateAllowAgents() → 校验 allowAgents 引用完整性
  ├─ 对每个 Agent 调用 syncSubAgentRoster(agentId, list)
  │   ├─ _syncSkillLinks(skillIds, workspace)     ← 管理 junction 链接
  │   ├─ _syncToolsMd(agentId, list, skillIds, ws) ← 重写 TOOLS.md 系统段落
  │   ├─ _syncIdentityMd(agentId, list, ws)        ← 生成 IDENTITY.md
  │   ├─ _syncBootstrapMd(agentId, list, ws)       ← 生成 BOOTSTRAP.md
  │   └─ _cleanAgentsMd(ws)                        ← 清理 AGENTS.md 中旧版段落
  ↓
前端收到 SSE: agents-updated → Api.fetchAgents() 刷新列表
```

### 1.2 配置变更同步链路

```
openclaw.json 文件变更（外部编辑 / CLI 操作）
  ↓
server.js fs.watch → 检测 eventType === 'change' → 1 秒防抖
  ↓
rosterSync.syncAllRosters() + agentRoutes.invalidateCache()
  ↓
sseManager.broadcast({ type: 'agents-updated' })
  ↓
前端 WsBridge 监听 → Api.fetchAgents() + Api.fetchModels()
```

### 1.3 技能卸载链路

**路径 A：从 Agent 解绑技能（Agent 编辑 → 取消勾选）**

```
Api.updateAgent(agentId, { skills: ['web-search'] })  ← 原来有 ['web-search', 'zhihu-search']
  ↓

agent-routes.updateAgent() → agentList[i].skills = ['web-search'] → store.writeConfig()
  ↓
rosterSync.syncAllRosters()

  │   → zhihu-search junction 被移除 ✓
```

```
  ├─ rosterSync.unbindSkillFromAll(skillId)
  │   → 从所有 Agent 的 skills 数组中移除 → writeConfig → syncAllRosters
```

## 三、发现的问题

### 问题 1（BUG）：_syncSkillLinks 保留了不该存在的 junction

**严重性：中**
**位置：roster-sync.js → _syncSkillLinks() 第 49-79 行**

**现象：**
- main Agent 没有配置任何 skills，但 workspace/skills 下有 9 个 junction
- 设计师小王 配置了 2 个 skills，但 workspace/skills 下有 3 个 junction（多了 md2wechat）

**根因：**
第 58-59 行的清理条件：
```js
if (skillIds.indexOf(name) < 0 && resolved.indexOf(globalSkillsDir) < 0) {
  // 移除
}
```
条件是「不在 skillIds **且** 不指向全局技能目录 → 才移除」。
反过来意味着：只要 junction 指向全局技能目录，即使在 skillIds 之外也不会被移除。

**正确逻辑应该是：**
不在 skillIds 中 → 移除（无论指向哪里）。
或者更精确：不在 skillIds 中 → 移除；但如果要移除的 junction 指向的目录还被其他 Agent 引用，全局技能目录本身不受影响（本来就不该删全局目录）。

**影响：**
- Agent 会"看到"不属于自己的技能，可能导致 LLM 误调用
- TOOLS.md 系统段落是正确的（只列出配置的 skills），但 workspace/skills 目录有多余的 junction，OpenClaw Gateway 读取 workspace 时可能扫描到多余技能

**修复建议：**
```js
// 改为：不在 skillIds 中 → 移除，无论指向哪里
if (skillIds.indexOf(name) < 0) {
  try { fs.rmSync(managed[name], { recursive: true, force: true }); } catch (e) {}
}
```

**⚠️ 修复副作用（Trae 审查指出）：**
main Agent 在 openclaw.json 中没有 `skills` 字段，`syncSubAgentRoster` 调用时 `target.skills || []` = `[]`。修复后 main Agent 的 workspace/skills 目录会被清空 — 这是**技术上的正确行为**（main 没有配置技能就不该有）。

~~**原建议（已否定）：** 先给 main Agent 补 skills 字段再改代码。~~
**否定原因（用户确认）：** 这是个性化适配，不是通用修复。为了兼容某一套存量配置而在代码里加特殊分支，违反"安装路径是唯一真相源"原则。正确做法是直接改清理条件，`syncAllRosters()` 会自动将磁盘状态对齐到配置的真实状态。如果存量数据需要调整（比如给 main Agent 加技能），那是用户自己在 Web UI 上操作的事，不是代码该兜底的事。

**修复方案：**
1. 改 _syncSkillLinks 清理条件为 `if (skillIds.indexOf(name) < 0)`
2. 重启服务或触发一次 syncAllRosters()，磁盘状态自动对齐
3. 如果用户希望 main Agent 拥有某些技能，通过 Web UI 的 Agent 编辑界面正常配置即可

### 问题 2（体验）：TOOLS.md 中出现两个 "## 技能" 段落

**严重性：低**
**位置：roster-sync.js → _buildSkillSection() 与用户手动内容的冲突**

**现象（以设计师小王为例）：**
```
## 技能              ← 用户手写段落（1-91行，非常详细，含工作流、触发场景等）
...详细内容...

<!-- system-sync-start -->
## 技能              ← 系统自动段落（92-115行，精简版，只有名称）
...精简内容...
<!-- system-sync-end -->
```

**根因：**
- 用户（或其他工具）在 TOOLS.md 中手动编写了详细的技能文档
- _buildSystemSection() 在 system-sync 标记内又生成了一个同名的 "## 技能" 段落
- _stripSystemSection() 只剥离标记内的内容，不影响用户段落
- 结果：同一个文件中出现两个 "## 技能"，LLM 读到两份技能说明

**影响：**
- 对 LLM 来说两份信息可能冲突（一份详细，一份精简），造成困惑
- 浪费 token（系统段落是冗余的，因为用户段落已经包含了更详细的信息）

**修复建议：**
方案 A（推荐）：系统段落检测到用户段落已存在 "## 技能" 时，跳过自动生成技能段落，只同步团队成员段落
方案 B：系统段落改用不同的标题，如 "## 可用技能速查"，避免重名

### 问题 3（性能）：技能扫描存在冗余 I/O

**严重性：低**
**位置：fs-store.js → scanGlobalSkills(), scanExtraDirsSkills()**

**现象：**
- listAgents() 调用 _resolveSkills() → scanGlobalSkills() + scanExtraDirsSkills()
- listSkills() 也调用 scanGlobalSkills() + scanExtraDirsSkills()
- syncAllRosters() 中每个 Agent 的 _syncToolsMd → _buildSkillSection → 又调用 scanGlobalSkills() + scanExtraDirsSkills()
- 每次扫描都重新 fs.readdirSync + fs.readFileSync(SKILL.md)

**根因：**
扫描函数是无状态的纯函数，没有缓存。在有 7 个 Agent + 11 个全局技能的当前规模下，一次 syncAllRosters() 会触发约 7 × 2 = 14 次全局技能目录扫描。

**影响：**
当前规模下性能可接受（14 次目录扫描 < 100ms），但如果 Agent 或技能数量增长，会成为瓶颈。

**修复建议：**
在 syncAllRosters() 入口处扫描一次全局技能，作为参数传递给后续函数。或在 roster-sync.js 中添加简单的请求级缓存。

### 问题 4（健壮性）：_syncSkillLinks 不必要的 junction 重建

**严重性：低**
**位置：roster-sync.js → _syncSkillLinks() 第 81-99 行**

**现象：**
每次 syncAllRosters() 都会对所有技能执行：先检测是否存在 → 存在就跳过 → 不存在就创建。
但第 83-86 行的逻辑是：
```js
try {
  const stat = fs.lstatSync(linkPath);
  if (stat.isSymbolicLink()) return;  // 已存在且是链接 → 跳过 ✓
  fs.rmSync(linkPath, { recursive: true, force: true });  // 存在但不是链接 → 删除
} catch (e) {}
// 然后创建 junction
```

**这段逻辑是正确的** — 已存在的 junction 不会被重建。但问题出在第 63-77 行的"孤立目录替换"逻辑：
如果一个技能目录是普通目录（非 junction），但它在全局技能目录中有对应项，会被删除后重建为 junction。这在首次同步时是合理的，但如果某次同步因权限问题失败，下次同步会重复这个操作。

**影响：** 轻微。当前实现已足够健壮。

### 问题 5（BUG）：fs.watch 只处理 'change' 事件 — 原子写入触发的 rename 被忽略

**严重性：中高（Trae 审查提升）**
**位置：server.js 第 201 行**

**现象：**
```js
fs.watch(OPENCLAW_CONFIG, function (eventType) {
  if (eventType !== 'change') return;
```

**关键链条：**
1. `writeConfig()` 使用原子写入：先写 `.tmp` 文件，再 `fs.renameSync(tmpPath, OPENCLAW_CONFIG)` 覆盖原文件
2. `rename` 操作在 Windows 上触发 fs.watch 的 `'rename'` 事件（不是 `'change'`）
3. server.js 过滤了 `eventType !== 'change'`，所以 `rename` 事件被丢弃
4. **结论：Web UI 内部通过 writeConfig() 写入 openclaw.json 后，fs.watch 监听器可能根本不会触发同步**

**为什么之前没有暴露：**
所有 API 路径（createAgent、updateAgent、deleteAgent、handleSetup 等）在调用 writeConfig() 之后，都**显式调用了 `syncAllRosters()`**。所以 fs.watch 从未是唯一依赖的同步通道 — 它只是"外部编辑的兜底"。但如果用户用外部编辑器（VS Code、Notepad++ 等）手动编辑 openclaw.json，很多编辑器的保存策略也是原子写入（write-to-temp + rename），同样会触发 rename 而非 change，导致兜底失效。

**修复建议：**
```js
// 接受 change 和 rename 两种事件
if (eventType !== 'change' && eventType !== 'rename') return;
```
或更简洁地直接移除过滤条件（防抖已经能抑制重复触发）。

### 问题 6（设计）：技能安装缺少全局技能注册机制

**严重性：信息项**

**现象：**
当前技能的"安装"就是在全局 skills 目录下放一个包含 SKILL.md 的文件夹。没有注册表、没有版本管理、没有依赖检查。
Web UI 的技能列表通过扫描目录动态生成（scanGlobalSkills），所以放进去就能被发现。

**评价：**
这符合"不重复造轮子"的原则 — OpenClaw 本身就是这么设计的，Web UI 只是读取和展示。但作为面向 GitHub 公开发布的产品，用户可能会问"怎么安装第三方技能"。目前的答案是"把文件夹放到 ~/.openclaw/skills/ 下"，这足够简单，但缺少一个"技能市场"或"一键安装"的体验。

这不是 bug，是产品层面的演进方向，当前阶段不需要改动。

### 问题 7（Trae 补充）：技能名称不一致 — 目录名 vs 配置引用

**严重性：中**
**来源：Trae 审查反馈**

**现象：**
全局技能目录中存在 `flowus-agent` 和 `flowus-agent-skills` 两个独立目录。配置中知识库小知绑定的是 `flowus-agent`。如果用户安装技能时目录名和配置中引用的 ID 不一致（比如从 GitHub 克隆时仓库名带 `-skills` 后缀），会导致：
- scanGlobalSkills 按目录名注册技能 ID
- Agent 配置的 skills 数组引用的是另一个 ID
- 结果：技能显示为 "⚠ 未找到"，junction 创建失败

**根因：**
当前 SKILL.md 没有 frontmatter（如 `name: flowus-agent`），技能 ID 完全由目录名决定。如果技能发布者的仓库名和用户期望的 ID 不一致，就会出问题。

**影响：**
这是"安装第三方技能时可能踩的坑"。当前用户（你自己手动管理）不会遇到，但 GitHub 公开发布后，其他用户 clone 技能仓库时目录名可能不一致。

**修复建议：**
~~方案 A：在 scanGlobalSkills / _parseSkillMd 中支持 SKILL.md 的 frontmatter `id:` 字段~~ — **需重新评估**，frontmatter 覆盖本质上是给个别命名不一致的技能打补丁，违反通用性原则。

方案 C（最小改动、最通用）：在 AgentModal 的技能列表中，对于 missing 技能显示完整的期望 ID，方便用户排查目录命名问题。这是纯 UI 提示，不改变核心逻辑。

## 六、核心修复原则（用户确认）

> **安装路径是唯一真相源。**

1. **通用性优先，不做个性化适配。** 虾指挥是面向 GitHub 所有用户的产品，不是某个人的私有工具。任何修复都必须是通用解法，不能为了兼容某一套存量配置而扭曲正常逻辑。

2. **安装即真相，卸载即清除。** 安装流程生成什么配置，卸载流程就清除什么配置。配置的生命周期严格跟随安装/卸载路径，不存在"历史遗留"需要特殊处理的情况。

3. **存量数据差异通过数据迁移解决，不通过改代码适配。** 如果现有用户的磁盘状态与修复后的正确逻辑不一致（比如 main Agent 没有 `skills` 字段却有 junction），那是数据迁移的问题——跑一次 `syncAllRosters()` 让状态自动对齐即可，不需要在代码里加 if-else 绕过。

4. **硬编码是红线。** 为了贴合某个特定配置而写特殊分支，就是硬编码。不管它看起来多"无害"，都是在制造技术债。

**此原则已同步到项目指导文件 `_qoderwork-notes/修复原则.md`，后续所有修复必须遵守。**
