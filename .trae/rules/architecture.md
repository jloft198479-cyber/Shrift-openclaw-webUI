# 架构原则

> 本文档定义代码和系统设计的基本原则。与工作原则分开，专注技术决策。

---

## 核心原则

### 真理源自一处，全局引用
- 配置、状态、常量只有一份，其他地方只引用
- `State.js` 是唯一的状态管理中心
- `State.setState()` → 事件通知 → 组件响应，单向数据流

### 高内聚、低耦合
- 一个文件只做一件事
- 组件不直接操作其他组件的 DOM
- 控制器不直接知道视图的细节，视图不直接调 API

### 模块化、组件化、原子化
- UI 组件可独立渲染、独立销毁（有 `init/destroy`）
- 工具函数是纯函数，不依赖全局状态
- 功能单元可单独测试

### 更轻、更快、更强
- 不引入不必要的依赖
- DOM 操作节流（requestAnimationFrame）
- 错误边界保护，一处崩溃不影响全局

### 重结构，轻代码
- 好的结构比多的代码重要十倍
- 先搭架子，再填内容
- 拆分优于堆砌

### 资源节约原则
- **产品设计要替用户节约资源**——省 token、省内存、省 CPU、省算力
- 功能完成 ≠ 任务完成，资源消耗也是质量指标
- 堆砌代码 = 浪费用户资源 = 工作不合格
- 重复逻辑必须合并，双重处理必须消除
- 代码简洁不是风格偏好，是对用户资源的尊重

#### 决策阶梯（写代码前必须过）

在写任何代码之前，从第一级开始，**停在第一个成立的层级**：

1. **这东西需要存在吗？** —— 推测性需求 = 不做，一句话说明即可（YAGNI）
2. **标准库/运行时能做吗？** —— 用标准库，不自己造轮子
3. **平台原生功能能覆盖吗？** —— 用原生（如 `<input type="date">` 不引日期库，CSS 能做的不写 JS）
4. **已安装的依赖能解决吗？** —— 用现有依赖，不为几行代码引入新依赖
5. **能一行搞定吗？** —— 一行
6. **以上都不行** —— 写最少能工作的代码

阶梯是反射动作，不是研究课题。两级都成立 → 取更高级，继续前进。

### 绝不硬编码
- **绝不硬编码**——除非万不得已，否则任何数据、配置、路径、命令、技能列表都不允许写死在代码或文档中
- 所有动态内容必须从单一数据源派生，禁止在 AGENTS.md、system prompt、代码中硬编码技能命令、agent 列表、搜索工具等
- 硬编码 = 绕过"真理源自一处"原则 = 数据不一致 = 角色混乱、技能乱用
- **违反此条 = 工作不合格**

### 契约设计
- 模块间交互必须通过明确契约（接口签名、事件格式、数据结构），不允许隐式依赖
- API 契约：请求/响应结构、状态码、错误格式必须稳定，变更需版本化
- 事件契约：事件名称和 payload 结构必须定义清晰
- 数据契约：数据结构的 required/optional 字段、默认值必须明确
- 契约一旦确定，消费者只依赖契约，不依赖实现细节——**依赖实现细节 = 脆弱耦合**

### 退化安全
- 任何外部依赖（Gateway、WebSocket、文件系统）都可能失败，**必须有 fallback**
- 降级策略必须提前设计，不能等出了问题再补
- 降级路径必须可测试——手动模拟故障，验证降级行为
- 用户永远不应看到空白页面或无响应——至少给出明确的错误提示和恢复建议
- 错误边界：一个组件崩溃不应拖垮整个页面

#### 绝不简化掉的清单

决策阶梯追求精简，但以下内容**永远不能被简化掉**：

- 信任边界的输入校验（用户输入、外部 API 响应）
- 防止数据丢失的错误处理
- 安全措施（路径遍历防护、XSS 防护、token 校验）
- 无障碍基础（可访问性）
- 用户明确要求保留的功能
- 硬件/物理世界的校准参数（时钟漂移、传感器偏差）

### 简化标记约定

当按决策阶梯做了刻意简化时，用 `simp:` 注释标记，说明上限和升级路径：

```js
// simp: 全局锁，单账户吞吐量不足时改为 per-account 锁
```

```css
/* simp: 硬编码颜色，主题化时提取为 CSS 变量 */
```

规则：
- 格式：`simp: <已知上限>, <升级触发条件>`
- 有上限无升级路径的标记为 `simp: <上限>, no-upgrade`——这些最易腐烂，需优先关注
- 简单的一行代码无需标记，YAGNI 也适用于标记本身
- 标记是意图声明，不是技术债——让简化可追溯，不被误认为疏忽
