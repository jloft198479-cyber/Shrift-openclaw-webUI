## 一、VPN 上网经验总结

> 创建：2026-05-31 | 基于 2026-05 月实际使用经验
> 适用环境：Windows 10 + Git Bash + yunti/xray VPN

### 1.1 网络架构

```
VPN 软件（云梯/yunti）
    ↓
xray-core（2 个进程）
  ├── PID xxxx → TCP 代理  → 127.0.0.1:9098（HTTP/SOCKS 混合代理）
  └── PID xxxx → DNS 代理  → 127.0.0.1:9096 / 9099（SOCKS）
        ↓
Windows 系统代理 → 127.0.0.1:9098（"VPN 已开启" = 这个打开）
路由器 DNS → 192.168.1.1 → ISP DNS（国内 ISP 会劫持 github.com 等域名）
```

关键路径：所有流量想出去，要么走 `127.0.0.1:9098` 这个代理，要么直连。直连会被 ISP 劫持。

### 1.2 核心经验：两套网络路径

| 程序类型 | 走什么网络路径 | VPN 开 = 自动能上外网？ |
|---------|--------------|----------------------|
| 浏览器（Chrome/Edge） | **Windows 系统代理** | 是，自动走 VPN |
| Git Bash 里的 curl/wget/gh | **环境变量** `HTTPS_PROXY` | **不自动**，需手动设 |
| Claude Code 里的 Bash 工具 | **环境变量** `HTTPS_PROXY` | **不自动**，每次都要设 |
| 普通 Windows 应用（大多数） | Windows 系统代理 | 大部分自动走 |
| git 命令行 | git 全局配置 `http.proxy` | **不自动**，需单独配 |

**一句话记：** 浏览器能上 Google 不等于命令行也能上，它们是两套完全独立的网络路径。

### 1.3 各工具 VPN 访问配置

**浏览器（Chrome/Edge）** — VPN 开了就能上，不需要任何额外配置。

**Git Bash 终端** — 每次新开 Bash，必须先设代理：

```bash
export HTTPS_PROXY=http://127.0.0.1:9098 HTTP_PROXY=http://127.0.0.1:9098
```

持久化方案已写入 `~/.bashrc`，但 Claude Code 和某些自动化工具每次调用都是独立 `bash -c`，不加载 `.bashrc`，必须手动 export。

**git 命令行** — 已配全局代理（一劳永逸）：

```bash
git config --global http.proxy http://127.0.0.1:9098
git config --global https.proxy http://127.0.0.1:9098
```

**gh CLI** — 使用前必须设环境变量，因为 gh 不走 git 全局代理。

**curl/wget** — 设了 `HTTPS_PROXY` 环境变量后自动走代理。

### 1.4 VPN 连通性测试

快速测试：

```bash
curl -sI --max-time 10 --proxy http://127.0.0.1:9098 https://www.google.com
# 返回 HTTP/1.1 200 OK → VPN 工作正常
```

分层测试：

| 测试项目 | 命令 | 正常结果 |
|---------|------|---------|
| Google | `curl -sI --proxy http://127.0.0.1:9098 https://www.google.com` | HTTP 200 |
| GitHub | `curl -sI --proxy http://127.0.0.1:9098 https://github.com` | HTTP 301/200 |
| GitHub API | `curl -sI --proxy http://127.0.0.1:9098 https://api.github.com` | HTTP 200 |
| DNS（防劫持） | `nslookup github.com 8.8.8.8` | 20.205.243.166 |
| DNS（ISP 劫持检测） | `nslookup github.com 192.168.1.1` | 返回 127.0.0.1 = 被劫持 |

### 1.5 常见问题排查

**浏览器能上外网，命令行不行** — 浏览器走系统代理，命令行没走。设环境变量即可。

**昨天能推 GitHub，今天不能** — 按可能性排序：gh 的 token 被删了、DNS 被 ISP 劫持、当前 Shell 没设代理环境变量。

**DNS 被 ISP 劫持** — 中国 ISP 对 GitHub 等国外域名做 DNS 劫持是国内常态，不是故障。设置 `HTTPS_PROXY` 走 VPN 代理即可绕过，VPN 本身会处理 DNS 查询。不要尝试修复路由器。

### 1.6 DNS 劫持检测速查

```bash
nslookup github.com 192.168.1.1   # ISP DNS — 被劫持时返回假 IP
nslookup github.com 8.8.8.8       # Google DNS — 始终返回真实 IP
nslookup github.com 1.1.1.1       # Cloudflare DNS
```

已知被劫持域名（中国 ISP 常态）：`github.com`、`raw.githubusercontent.com`、部分 Google 服务。

### 1.7 一键测试脚本

```bash
#!/bin/bash
# VPN 连通性测试脚本
PROXY=http://127.0.0.1:9098
PASS=0
FAIL=0

test_url() {
    local desc=$1 url=$2
    local code=$(curl -sI --max-time 10 --proxy "$PROXY" "$url" 2>/dev/null | head -1 | awk '{print $2}')
    if [ "$code" = "200" ] || [ "$code" = "301" ] || [ "$code" = "302" ]; then
        echo "  OK $desc -- HTTP $code"
        PASS=$((PASS+1))
    else
        echo "  FAIL $desc -- code: $code"
        FAIL=$((FAIL+1))
    fi
}

echo "===== VPN 连通性测试 ====="
echo "代理: $PROXY"
echo "时间: $(date)"
echo ""
test_url "Google" "https://www.google.com"
test_url "GitHub" "https://github.com"
test_url "GitHub API" "https://api.github.com"

echo ""
echo "DNS 检测:"
github_ip=$(nslookup github.com 8.8.8.8 2>/dev/null | grep -A1 "Name:" | tail -1 | awk '{print $2}')
echo "  github.com @8.8.8.8 -> $github_ip"
echo ""
echo "结果: $PASS 通过, $FAIL 失败"
[ $FAIL -eq 0 ] && echo "VPN 工作正常！" || echo "VPN 部分异常，请检查"
```

## 二、Shrift (瞎指挥) 前端代码全维度评审

### 2.1 项目概览

| 指标 | 数值 |
|------|------|
| 前端 JS 文件 | 32 个（含 3 个三方库） |
| 后端 JS 文件 | 11 个 |
| 前端框架 | 无（原生 Vanilla JS） |
| 依赖 | 仅 `ws`（后端）+ `marked.js` + `DOMPurify` + `turndown`（前端） |
| 构建工具 | 无（直接 `<script defer>` 加载，cache busting 用版本号 query string） |

### 2.2 主从 Agent 调用逻辑评审

**设计亮点：**

Hub-and-Spoke 调度模型清晰：`main` agent 作为中枢，子 agent 通过 `allowAgents` 白名单注册。Roster 同步机制（`roster-sync.js`）自动将团队成员和技能信息写入各 agent 的 `TOOLS.md`（用 `<!-- system-sync-start/end -->` 标记），同时自动生成 `IDENTITY.md` 和 `BOOTSTRAP.md`。Proxy 注入（`proxy.js`）：请求到达时自动读取对应 agent 的 AGENTS.md 注入 system message，实现了身份隔离。

**仍存在的问题：**

| # | 严重度 | 问题 | 位置 |
|---|--------|------|------|
| A1 | 高 | `@mention` 分发完全依赖大模型理解指令，无前端兜底校验。如果模型忽略了 `@agent_id` 指令，用户感知为"召唤失败"但无任何提示 | `chat-controller.js` |
| A2 | 中 | `interactionMode` dispatch 模式硬编码为 `'main'`——这是设计意图（main 作为调度者），但如果用户删除了 main agent 则请求 404，缺少防御性检查 | `chat-controller.js:49` |
| A3 | 中 | Agent 切换检测依赖 SSE 流中的 `model` 字段以 `openclaw/` 开头，这个协议约定是隐式的，Gateway 升级可能破坏 | `api.js` |
| A4 | 低 | `ws-client.js` 中的 `chatSend()` / `chatHistory()` 方法已实现但从未被调用，属于死代码 | `ws-client.js` |

### 2.3 架构设计评审

**整体拓扑：**

```
Browser (SPA)
  ├── SSE ← /api/events ← sse-manager ← ws-client (WebSocket) ← OpenClaw Gateway
  ├── REST → /v1/chat/completions → proxy → Gateway HTTP (SSE stream)
  └── REST → /api/* → routes → agent-routes / fs-store
```

**优点：** 服务端依赖图是干净的 DAG，无循环依赖；模块职责划分合理（`fs-store` 数据层、`roster-sync` 同步层、`agent-routes` API 层三层分离）；零构建依赖，部署极简。

**问题清单：**

| # | 严重度 | 问题 | 位置 |
|---|--------|------|------|
| B1 | 高 | 前端无模块系统。30+ 全局变量/函数通过 `<script defer>` 标签顺序加载，任何顺序变动都会导致崩溃。`utils.js:301-327` 仍导出大量全局别名（`escapeHtml`, `uid`, `scrollToBottom` 等） | `index.html`, `utils.js` |
| B2 | 高 | State 无不可变性保证，无批处理机制。虽然已引入 pub/sub 事件和变更检测（值不变时不触发），但对象仍被原地修改，连续 `setState()` 仍导致级联渲染 | `state.js` |
| B3 | 中 | 3 个组件是死代码：`virtual-list.js`（397 行，已加载但从未调用）、`lazy-loader.js`（108 行）、`error-handler.js`（168 行）。另有 `model-picker.js` 作为孤立文件存在于磁盘但未加载 | 多个文件 |
| B4 | 低 | 无构建步骤意味着无 tree-shaking、无压缩（已有版本号 cache busting） | `index.html` |
| B5 | 低 | State 同时支持扁平访问和分组访问（15 对 getter/setter），双层映射增加理解成本 | `state.js` |

### 2.4 模块解耦评审

**服务端耦合度：良好。** `fs-store.js` 和 `sse-manager.js` 是无依赖的叶子模块；`proxy.js` 通过参数注入接收 store，实现了控制反转。

**前端耦合度：较差。** 核心问题是隐式全局耦合——`State`、`Api`、`Utils.*`、`SessionStore`/`SessionManager`、`MessageRenderer` 等全局符号被几乎所有模块消费。

| # | 严重度 | 问题 | 位置 |
|---|--------|------|------|
| C1 | 高 | `StreamRenderer` 直接引用 `ChatView._activeChatCleanup`（该属性不存在，实际是 `ChatController._activeChatCleanup`），跨组件访问私有属性且引用错误 | `stream-renderer.js:98-109` |
| C2 | 高 | `interaction-bindings.js`（504 行）仍是单体文件，虽然内部已按功能分组（`_bindButtons`、`_bindInput`、`_bindShortcuts` 等）且有 `destroy()` 清理，但所有 DOM 事件绑定仍集中在一个文件中 | `interaction-bindings.js` |
| C3 | 中 | `ChatController` → `AttachmentBar.uploadAll()` → `SessionInteraction.ensureSession()` → `MessageRenderer.appendMessage()` 链式调用形成隐式依赖链 | `chat-controller.js` |
| C4 | 中 | 多处使用 `document.querySelector` 硬编码 DOM 选择器，组件间通过 DOM 结构耦合 | 多个文件 |

### 2.5 通信机制评审

SSE 事件桥（Server → Browser）：指数退避重连 3s → max 30s，EventSource 出错时主动 close 后手动重连，消除了双重重连竞争；死连接清理通过写错误自动移除。WebSocket 桥（Server → Gateway）：JSON-RPC 协议，25 秒心跳，subscribe 失败时回退到 5 秒 HTTP 轮询。

| # | 严重度 | 问题 | 位置 |
|---|--------|------|------|
| D1 | 高 | SSE 响应设置了 `Access-Control-Allow-Origin: *`，无 CSP 头 | `sse-manager.js:29` |
| D2 | 中 | Session 保存是 fire-and-forget，页面关闭前 fetch 未完成则服务端数据滞后 | `session-manager.js` |
| D3 | 中 | 无请求去重：`Api.fetchAgents()` 可从 SSE 重连、`agents-updated` 事件、app 初始化等多个来源并发触发，无防抖或去重 | `api.js` |
| D4 | 低 | `WsBridge` 的 `on()`/`off()` 事件系统已定义但无订阅者 | `ws-bridge.js` |

### 2.6 子 Agent 管理评审

**创建流程：** 名称 → ID 生成（去重 + 通用 ID 过滤） → 工作区目录创建（按显示名 `workspace-{safeName}`） → AGENTS.md + TOOLS.md 写入 → config 注册 → allowAgents 更新 → roster 同步。新增工作区重复检测（409 错误）。

**亮点：** Skill symlink 同步机制（`roster-sync.js`，Windows 用 junction，其他平台用 dir symlink，失败时回退到文件复制）；`_validateAllowAgents()` 每次同步清理悬空引用和自引用；Roster 同步现在将团队/技能信息写入 `TOOLS.md` 而非 `AGENTS.md`（避免破坏 LLM provider prefix cache）。

| # | 严重度 | 问题 | 位置 |
|---|--------|------|------|
| E1 | 高 | Agent ID 生成策略对纯中文名称仍不友好：正则 `/[^a-z0-9_-]/g` 会剥除所有非 ASCII 字符，中文名称产生空 ID 后回退到 `agent-{randomId}`，可读性差。已增加 `_GENERIC_IDS` 防滥用和长度检查作为缓解 | `agent-routes.js:137-151` |
| E2 | 高 | 同步文件 I/O 阻塞事件循环：`fs.readFileSync`、`fs.writeFileSync` 遍布 `fs-store.js`、`roster-sync.js`、`routes.js`、`launcher.js` 等多个文件 | 多个文件 |
| E3 | 中 | `_saveAgentList()` 的 else 分支将整个 `data.agents` 对象替换为数组，可能丢失 `defaults.contextInjection` 和 `defaults.model` 等配置 | `agent-routes.js:133-134` |
| E4 | 中 | Config 文件监视竞态：`fs.watch` 监听 `openclaw.json`，虽有 1 秒 debounce，但 `syncAllRosters()` 调用 `readFileSync` 时如果外部进程正在写文件，可能读到不完整内容。自身的 `writeConfig` 用了 tmp+rename 原子写入，但外部写入者不受控 | `server.js:198-220` |
| E5 | 低 | Roster sync 静默吞错 | `roster-sync.js` 多处 |

## 三、Skill 代码执行原则

1. **单一职责（Keep Focused）** — 一个 Skill 只解决一个特定的、可重复的特定工作流（如"Changelog 生成"或"前端代码审查"），切忌做成试图包揽一切的"大杂烩"。

2. **渐进式加载（Context Optimization）** — 利用好 `REFERENCE.md` 拆分不常用的长文本知识。默认只读取 `skill.md` 的描述，只有在触发时才会加载正文，从而最大化节省 Token。

3. **无感组合性（Composability）** — 编写规范时不要显式依赖另一个 Skill。优秀的 Skill 应当可以被自动地与其他 Skill 串联协同工作。

4. **禁止硬编码（Security First）** — 严禁在 Skill 的脚本或文本中硬编码任何敏感信息（如 API Key、密码或私有凭证），外部交互应通过 MCP 连接器进行。

5. **增量测试（Incremental Testing）** — 先从纯文本的 Markdown 指示开始测试，确保能够精准触发后，再加入更复杂的代码执行脚本。

## 四、子 Agent 注册机制分析

### 4.1 创建流程

用户创建一个子 agent 时，代码执行以下链路：

```
创建子 agent (agent-routes.js:createAgent)
      │
      ├── 1. openclaw.json 注册
      │     agent 写入 agents.list[]
      │     同时 _ensureInAllowAgents() 把 ID 追加到
      │     main agent 的 subagents.allowAgents[]
      │
      ├── 2. 工作区创建
      │     mkdir workspace-{safeName}（按显示名，非 ID）
      │     写入 AGENTS.md + TOOLS.md
      │     检查工作区是否已存在（409 防重复）
      │
      └── 3. Roster 同步 (roster-sync.js)
            syncAllRosters() → 校验 allowAgents + 同步每个 agent
            每个 agent: syncSkillLinks → syncToolsMd → syncIdentityMd → syncBootstrapMd
```

### 4.2 子 Agent 发现机制

子 Agent 的发现依赖**配置层 + 环境文件**的组合：

**配置层（结构化注册）** — `allowAgents` 是 OpenClaw Gateway 的权限控制字段。当 main agent 调用 `sessions_spawn(agentId: "translator")` 时，Gateway 检查白名单——不在里面的 ID 会被拒绝。这条通道是确定性的，不依赖大模型。

**环境文件（TOOLS.md）** — `roster-sync.js` 自动将团队成员列表和技能信息写入各 agent 的 `TOOLS.md`（用 `<!-- system-sync-start/end -->` 标记包裹），main agent 据此了解有哪些专家可用。

**重要变更：** 早期版本将子 Agent 列表写入 `AGENTS.md` 的 `## Sub-Agents` 段落，后来被刻意移除。原因是 OpenClaw 原生 `sessions_spawn` 发现机制不依赖 AGENTS.md 中的子 Agent 列表，写入是冗余的，且会破坏 LLM provider 的 prefix cache。现在 `_cleanAgentsMd()` 会主动清理 AGENTS.md 中残留的旧格式 Sub-Agents/Team Members/Skills 段落。

### 4.3 核心风险

"能不能调用"（权限）没问题，`allowAgents` 是结构化配置，Gateway 直接读取。"会不会调用"（意愿）仍不确定——取决于 main agent 的大模型是否通过 TOOLS.md 中的团队信息判断当前任务需要分发。这个不确定性在 OpenClaw Gateway 侧，不在虾指挥代码侧。

### 4.4 关键函数变化

与早期版本相比，`roster-sync.js` 经历了较大重构：`_toThirdPerson()` 和 `_readAgentSummary()` 被移除，`syncTeamRoster()` 变为空操作。新增了 `_buildTeamSection()`、`_buildSkillSection()`、`_syncToolsMd()`、`_syncIdentityMd()`、`_syncBootstrapMd()`、`_cleanAgentsMd()`、`_validateSkillRefs()` 等函数，整体职责从"同步 AGENTS.md"转向"同步 TOOLS.md + 自动生成 IDENTITY.md/BOOTSTRAP.md"。

## 五、OpenClaw 主从模式关键结论

> 摘自与虾指挥的对话，关于子 agent 独立 workspace 机制的讨论。

### 5.1 子 agent 可以拥有独立 workspace

`sessions_spawn` 有一个 `agentId` 参数，可以指定 spawn 到另一个已配置的独立 agent 实例上运行。官方文档明确写道：

> "Spawn under another configured agent id when allowed by `subagents.allowAgents`."
> "Native sub-agents still load bootstrap files from the target agent workspace."

这意味着子 agent 可以加载目标 agent 的 workspace 文件（包括独立的 MEMORY.md），同时依然保持主从/父子关系。

### 5.2 两种 spawn 模式对比

| 维度 | 默认 spawn（无 agentId） | agentId + allowAgents |
|------|-------------------------|----------------------|
| 是子 agent 吗 | 是 | 是 |
| 有没有独立 workspace | 没有 | 有（加载目标 agent 的 workspace） |
| 有没有独立 MEMORY.md | 没有 | 有 |
| 主从关系 | 父子 | 父子，结果汇报回父 |
| 需要配置 | 不需要 | 需要在 agents.list 注册目标 agent |

### 5.3 子 agent 注入限制

官方文档明确：子 agent 只注入 `AGENTS.md` 和 `TOOLS.md`，不注入 `SOUL.md`、`IDENTITY.md`、`USER.md`、`MEMORY.md`、`HEARTBEAT.md`、`BOOTSTRAP.md`。但 spawn 到另一个 agent 时加载的是那个 agent 的 workspace。

### 5.4 Workspace 目录结构

```
~/.openclaw/
├── workspace/                     ← 主 agent 的 workspace
│   ├── AGENTS.md / SOUL.md / IDENTITY.md / USER.md
│   ├── MEMORY.md / TOOLS.md / HEARTBEAT.md / BOOTSTRAP.md
│   ├── skills/
│   └── memory/
│
├── workspace-咪蒙/                ← 子 agent（按显示名命名）
│   ├── AGENTS.md / TOOLS.md / IDENTITY.md / BOOTSTRAP.md
│   ├── MEMORY.md（可配置独立记忆）
│   ├── SOUL.md / USER.md / HEARTBEAT.md
│   └── skills/
│
└── workspace-乔布斯/              ← 另一个子 agent
    └── ...同上结构...
```

每个 agent 在 `~/.openclaw/` 下直接有独立的 `workspace-{safeName}/` 目录（早期版本放在 `agents/` 子目录下，已扁平化）。目录名基于显示名而非 ID，改名时自动重命名目录。从文件结构上看它们是平级的——本质上是独立的 agent，只不过通过 `AGENTS.md` 配置拥有调度权。

### 5.5 配置示例

```json
{
  "agents": {
    "list": [
      {
        "id": "main",
        "subagents": {
          "allowAgents": ["agent-mpls0tivyzea"]
        }
      },
      {
        "id": "agent-mpls0tivyzea",
        "name": "咪蒙",
        "workspace": "~/.openclaw/workspace-咪蒙"
      }
    ]
  }
}
```

## 六、子 Agent 创建与自动注入流程

> 摘自 `创建子agent，自动注入系统` 对话。

创建子 Agent 时，系统自动执行以下链路：

```
用户创建子 Agent "小红"
       ↓
createAgent() 执行
       ↓
_ensureInAllowAgents(agentList, "小红")
       ↓
自动添加到 main.subagents.allowAgents
       ↓
_saveAgentList() 写入 openclaw.json
       ↓
rosterSync.syncAllRosters() 同步花名册
       ↓
Gateway 自动重载配置
```

这个流程确保了新创建的子 Agent 同时完成配置注册（allowAgents 白名单）和环境文件同步（TOOLS.md 团队信息更新），Gateway 自动感知变更无需重启。
