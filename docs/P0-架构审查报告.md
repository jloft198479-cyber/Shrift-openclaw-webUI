# P0 架构审查报告 — openclaw-web-ui

> 审查范围：宏观架构与核心逻辑缺陷（第一轮）
> 审查日期：2026-06-17
> 审查重点：多 Agent 协作与路由 / Token 消耗控制 / 通信衔接 / 数据闭环 / 生命周期
> 明确忽略：安全、可访问性、TS 迁移、测试、文档、DOM 性能、微小内存泄漏

---

## 一、架构总览（审查基础）

整体架构清晰，分层合理，是一份工程质量不错的原生 JS 实现：

- **状态中心**：`State.js` 单一状态树 + 事件订阅/发布，分组状态（ui/chat/agent/connection/model）+ 向后兼容 getter/setter，单向数据流。
- **通信双通道**：消息渲染走 SSE 流（`/v1/chat/completions` → `Api.chat` → `StreamRenderer`），状态/announce 走 `/api/events`（SSE EventSource）。后端再通过 WebSocket 连 Gateway，事件经 `session-sync` 检测文件增量后广播。
- **两种模式**：`dispatch`（智能调度，主 Agent 自动 spawn 子 Agent）与 `direct`（私聊指定 Agent）。
- **数据层**：配置 `openclaw.json` 原子写（tmp+rename），会话存 `sessions/*.json`，前端 localStorage 缓存 + 服务端持久化双写。

下面是 6 个 P0 级问题，按严重度排序。

---

## 二、P0 问题清单

### 🔴 P0-1 Token 消耗失控 — 历史消息零截断 + 图片 dataUrl 持久化重发

**位置**：`web/js/components/message-builder.js` `buildApiMessages` + `web/js/components/session-interaction.js` `saveUserMessage`

**问题**：

1. **历史消息全量发送，零截断**
   `buildApiMessages` 直接 `chatMessages.map(...)` 把整个 `session.messages` 发给 API，没有任何长度限制：
   ```js
   let apiMessages = chatMessages.map(function (m) { ... });
   ```
   对比 `session-manager.js` 的 `_renderSession` 有 `MAX_VISIBLE = 200` 的 UI 渲染上限，但 **API 侧没有任何截断**。会话越长，每轮请求携带的历史线性增长，Token 成本随之爆炸，最终触发模型上下文上限导致请求失败。

2. **图片 base64 dataUrl 被持久化并每轮重发**（更隐蔽的浪费）
   `saveUserMessage` 中：
   ```js
   if (a.dataUrl && a.dataUrl.length < 5120000) att.dataUrl = a.dataUrl;
   ```
   5MB 以下的 base64 图片被原样存入 `session.messages[].attachments`。后续每轮对话，`buildApiMessages` → `buildMultimodalMessage` 会把这些 dataUrl 重新构造为 `image_url` 发送。**同一张图片在后续每一轮都被重复发送**，而 base64 图片的 token 消耗极大（单张数千上万 token）。

**影响**：
- 长会话 Token 爆炸，成本飙升，且可能触发上下文上限导致请求失败。
- 图片重发是最隐蔽的浪费源——用户感知不到，但每轮都在烧钱。

**修复方向**：
- `buildApiMessages` 增加上下文窗口管理：保留最近 N 条 + 系统提示，或按 token 估算截断（参考 OpenAI 的 token 计数）。
- 图片附件：上传后只存路径，session 中不存 dataUrl；发送时用 `image_url: { url: window.location.origin + att.path }`（代码里已有这个分支，但 dataUrl 分支优先级更高）。或者发送后从 session 历史中剥离已发送图片的 dataUrl，仅保留路径引用。

### 🔴 P0-2 模式切换/会话切换不清理调度状态 — dispatching 残留锁死输入

**位置**：`web/js/controllers/chat-controller.js` + `web/js/controllers/session-manager.js`

**问题**：

`SessionManager.createSession` / `selectSession` / `exitAgentMode` 在切换会话时，会重置 `currentAgent` 和 `interactionMode`，但**都没有调用 `ChatController._clearDispatchState()`**，也没有显式设 `dispatching: false`：

```js
// createSession
State.setState({ currentSessionId: null, currentAgent: '', interactionMode: 'dispatch', messages: [] });
StreamRenderer.endStreaming();  // 只结束流式，不管 dispatching
```

如果用户在智能调度进行中（`State.dispatching === true`）切换/新建会话：
1. `dispatching` 状态残留为 `true`（`createSession` 没清它）。
2. 新会话里用户发消息 → `sendMessage` 开头：
   ```js
   if (State.streaming) return;
   if (State.dispatching) return;  // ← 直接静默返回
   ```
3. 用户看到输入框可用，发消息却**毫无反应，无任何提示**。

`selectSession` 的 `_renderSession` 同样只 `StreamRenderer.endStreaming()`，不清 dispatch 状态。`exitAgentMode` 也不清。

**影响**：
调度中途切会话后，新会话输入被永久静默锁死。用户完全不知道为什么发不出消息，难以自查，只能刷新页面。

**修复方向**：
在 `createSession` / `selectSession._renderSession` / `exitAgentMode` 中统一调用 `ChatController._clearDispatchState()`（或在 `State.setState` 切换 `currentSessionId` 时自动触发清理）。至少应在 `sendMessage` 的 `dispatching` 拦截处给用户一个 toast 提示"调度进行中，请稍候或取消调度"。

### 🔴 P0-3 session-sync 单槽位事件队列 — 并发 announce 丢消息

**位置**：`session-sync.js` `_scheduleRead` / `_pendingSessionKey`

**问题**：

`_scheduleRead` 用模块级单变量 `_pendingSessionKey` 和单个 `_retryTimer`：

```js
function _scheduleRead(sessionKey, frontendSessionId) {
  if (_retryTimer) {
    _pendingSessionKey = sessionKey;  // ← 直接覆盖，前一个 sessionKey 丢失
    return;
  }
  ...
}
```

智能调度模式下，主 Agent spawn 多个子 Agent，多个子 Agent 几乎同时完成，会产生多个 `sessions.changed` 事件。这些事件要么 sessionKey 不同（不同子 Agent），要么时序交错。当它们快速到达时：
- 只有最后一个被处理，中间的被 `_pendingSessionKey = sessionKey` 覆盖丢失。
- 即使 sessionKey 相同，`_doRead` 用文件 offset 增量读取，但前提是事件没被覆盖。

此外 `_doRead` 读取成功后立即推进 offset（`_fileOffsets[targetFile] = stat.size`），如果 broadcast 时前端 SSE 断连，这条消息也永久丢失（见 P0-6）。

**影响**：
多子 Agent 并发回传时，部分子 Agent 结果永久丢失，主从 Agent 消息归属不完整。这在"多 Agent 协作"这个核心场景下是致命的。

**修复方向**：
- 把单变量 `_pendingSessionKey` 改为队列（Set 或数组），按 sessionKey 去重入队，逐个处理。
- broadcast 失败或前端未连接时，保留 offset 不推进，等下次事件或前端重连后重试读取。

### 🔴 P0-4 direct 模式硬性屏蔽 announce — 子 Agent 结果全丢

**位置**：`web/js/controllers/chat-controller.js` `handleAnnounceResult` / `handleSubagentProgress` / `handleSubagentDone`

**问题**：

```js
handleAnnounceResult: function (messages, agentId, sessionId, offset) {
  ...
  if (State.interactionMode === 'direct') return;  // ← 直接返回
```

`handleSubagentProgress` 和 `handleSubagentDone` 同样：
```js
if (State.interactionMode !== 'dispatch') return;  // direct 模式全屏蔽
```

direct 模式（私聊指定 Agent）下，所有 announce / subagent-progress / subagent-done 事件被硬性忽略。

但 direct 模式的 Agent 内部**完全可能 `sessions_spawn` 子 Agent**——AGENTS.md 宪法里明确允许主 Agent 派子 Agent（"串行依赖/并行无依赖"编排）。子 Agent 完成后通过 announce 机制回传结果，结果被丢弃。用户在私聊模式下如果 Agent 自行 spawn 了子 Agent，子 Agent 的结果和进度在 UI 上完全不可见。

**影响**：
direct 模式下 Agent 自主编排的子 Agent 结果丢失，多 Agent 协作在私聊模式下断裂。这与"核心是灵活调用子 agent"的产品定位直接冲突。

**修复方向**：
重新审视 direct 模式的 announce 屏蔽逻辑。如果设计意图是"direct 模式只显示主 Agent 的流式回复"，那么至少应：
- 主 Agent spawn 子 Agent 后，SSE 流结束 → 应自动转入类似 dispatch 的等待态，接收 announce。
- 或在 direct 模式下也渲染 announce，只是不显示进度块。
- 当前"一刀切屏蔽"会导致 Agent 自主编排能力在私聊模式下完全失效。

### 🔴 P0-5 Agent 工作目录重命名与配置写入非原子 — 数据不一致

**位置**：`agent-routes.js` `updateAgent`

**问题**：

```js
fs.renameSync(ws, newWsPath);  // ① 先重命名物理目录
agentList[i].workspace = agentList[i].workspace.replace(currentDirName, expectedDirName);  // ② 改内存
...
if (_saveAgentList(data, agentList)) {  // ③ 写配置（tmp+rename，原子）
```

步骤 ①（重命名目录）和 ③（写配置）之间**非原子**：
- 如果 rename 成功但 writeConfig 失败（磁盘满、权限、tmp 写失败等），工作目录已改名但配置仍指向旧路径 → Agent 工作目录"丢失"（配置指向的旧路径已不存在）。
- rename 成功后、writeConfig 之前进程崩溃，同样不一致。
- `workspace.replace(currentDirName, expectedDirName)` 用字符串替换，若 workspace 路径中存在与 `currentDirName` 相同的子串（概率低但非零），会误替换。

注意：`writeConfig` 本身是原子的（tmp + rename），但"重命名目录"这个副作用不在 writeConfig 的事务内。

**影响**：
Agent 配置与实际工作目录脱钩，Agent 丢失其 AGENTS.md / 技能 / TOOLS.md 等所有工作区文件，且无法自动恢复。

**修复方向**：
- 调整顺序：先写配置（含新 workspace 路径）成功后，再重命名目录。若 rename 失败，回滚配置。
- 或先 rename 到临时名，写配置成功后再 rename 到最终名。
- `workspace` 路径替换改用基于 path 的精确替换，而非字符串 replace。

### 🔴 P0-6 SSE 断连期间事件无持久化 — announce 消息丢失

**位置**：`sse-manager.js` `broadcast` + `ws-bridge.js`（前端 SSE 重连）+ `session-sync.js`（offset 推进）

**问题**：

后端 `sseManager.broadcast` 是 fire-and-forget：
```js
broadcast(payload) {
  for (let i = 0; i < this.clients.length; i++) {
    try { this.clients[i].write(data); } catch (e) { dead.push(i); }
  }
}
```
没有事件缓冲/持久化，没有"未确认"机制。

前端 `WsBridge` 用 EventSource，断连后指数退避重连（3s~30s）。重连期间后端产生的 announce-result / subagent-progress / subagent-done 事件**直接丢失**（无客户端接收，broadcast 写入空）。

更严重的是 `session-sync.js` 的 offset 机制：
```js
_fileOffsets[targetFile] = stat.size;  // 读取成功后立即推进，不管 broadcast 有没有客户端
```
即使前端 SSE 断连，`session-sync` 仍在服务端跑，读取文件、推进 offset、broadcast（无人接收）。**重连后前端不会主动拉取"断连期间错过的事件"**，因为 offset 已推进，错过的消息不会再被读取。

**影响**：
网络抖动 / SSE 重连期间（3~30s），子 Agent announce 结果永久丢失，且无法恢复。本地单用户场景下网络抖动概率低，但 EventSource 重连本身（如服务端重启、浏览器休眠唤醒）会触发。

**修复方向**：
- 轻量方案：`session-sync` broadcast 时检查 `sseManager.clients.length`，为 0 时不推进 offset，等有客户端连接后重读。
- 中量方案：后端维护一个小的环形事件缓冲（最近 N 条），前端重连后通过 `Last-Event-ID` 拉取缺失事件。
- 前端重连后主动调一次 `/api/sessions/:id/sync`（路由已存在，`handleSessionSync`）补拉缺失消息——但当前 `readGatewayAssistantMessages` 是全量读取，需配合 offset 去重。

## 三、优先级与修复建议

| 编号 | 问题 | 严重度 | 修复难度 | 建议优先级 |
|------|------|--------|----------|------------|
| P0-1 | Token 消耗失控（无截断+图片重发） | 🔴 高 | 中 | **立即** — 直接影响成本和可用性 |
| P0-2 | 切换不清理 dispatching 状态 | 🔴 高 | 低 | **立即** — 几行代码，体验断裂 |
| P0-3 | session-sync 单槽位丢消息 | 🔴 高 | 中 | **立即** — 核心协作场景失效 |
| P0-4 | direct 模式屏蔽 announce | 🔴 高 | 中 | **立即** — 需明确产品意图后定方案 |
| P0-5 | 工作目录重命名非原子 | 🔴 中 | 低 | **尽快** — 调整顺序即可 |
| P0-6 | SSE 断连丢消息 | 🔴 中 | 中 | **尽快** — 本地场景概率低但不可恢复 |

**整体评价**：架构设计思路清晰，分层合理，状态中心和双通道通信是正确的选择。问题集中在"边界状态处理"——并发、切换、断连、模式交叉这些边界场景下的状态一致性。这正是多 Agent 协作系统最容易出问题的地方。建议优先修 P0-1 和 P0-2（影响面广、修复成本低），再攻 P0-3 和 P0-4（核心协作场景）。
