## 🔴 Blocker — 必须修复

### B-1 P2-3 message handler 未 clearTimeout，与提交说明不符

**位置**：`ws-client.js:129-137`

**问题**：
提交说明声称"message handler resolve/reject 时 clearTimeout，避免 timer 泄漏"，但实际代码**没有**在 resolve/reject 时 clearTimeout：

```js
// ws-client.js:129-137 — 实际代码
if (data.type === 'res' && pendingRequests[data.id]) {
  const pr = pendingRequests[data.id];
  delete pendingRequests[id];          // pr 引用即将丢失
  if (data.ok) {
    pr.resolve(data.payload);          // ← 未 clearTimeout(pr.timer)
  } else {
    pr.reject(new Error(...));         // ← 未 clearTimeout(pr.timer)
  }
  return;
}
```

`pr.timer` 存的定时器在 resolve/reject 后仍会跑完整个 timeoutMs（最长 60s）。虽然 timeout 回调里有 `if (pendingRequests[id])` 保护（已 delete 则跳过），**功能无害**，但：
1. 每个 WS 请求完成后都残留一个空跑定时器，直到 timeoutMs 才释放
2. 高频 WS 请求场景下累积大量空跑定时器
3. 提交说明与实际代码不符，属于实现遗漏

**修复**：
```js
if (data.type === 'res' && pendingRequests[data.id]) {
  const pr = pendingRequests[data.id];
  delete pendingRequests[data.id];
  if (pr.timer) clearTimeout(pr.timer);   // ← 补这一行
  if (data.ok) {
    pr.resolve(data.payload);
  } else {
    pr.reject(new Error(data.error ? data.error.message : 'Unknown error'));
  }
  return;
}
```

**严重度**：🔴 功能无害但必须修——提交说明声称做了实际没做，属于实现遗漏，且修复只需一行。

## 💭 Nit — 可接受，记录备查

### N-1 P3-1 滚动状态未按元素隔离

**位置**：`web/js/utils/utils.js:113-135`

`_scrollRafId` 和 `_pendingSmooth` 是 Utils 对象上的单一属性，如果两个不同的 `el` 同时调用 `scrollToBottom`，第二个调用会因 `_scrollRafId` 已存在而只更新 `_pendingSmooth` 然后 return，但 rAF 回调里用的是第一个调用的 `el`。

**实际影响**：应用中滚动容器基本只有 `#messages` 一个，风险极低。但如果未来出现多容器滚动场景，会串。记录备查，当前不修。

### N-2 P1-3 idle timeout 未覆盖 fetch 本身和非 SSE 分支

**位置**：`web/js/api.js`

idle timer 只在 `while (true) { resetIdleTimer(); await reader.read(); clearIdleTimer(); }` 循环里生效。以下路径未保护：
- `await fetch(...)` 本身（line 48）：若 Gateway 接受请求后很久不响应 HTTP 头，卡在此处
- 非 SSE 分支 `await res.json()`（line 59）：若非流式响应 hang 住

**实际影响**：有 `server.js` 的 180s socket 超时兜底，且这些路径通常很快返回。风险可接受。若要完善，可在 `fetch` 前也 `resetIdleTimer`，`res` 返回后 `clearIdleTimer`。

### N-3 P0-5 回滚配置的二次失败 + 字符串 replace 遗留

**位置**：`agent-routes.js:240-250`

两个遗留小问题：
1. **回滚二次失败**：rename 失败后回滚配置 `_saveAgentList(data, agentList)` 如果也失败，配置停留新路径但目录是旧路径。极端场景，概率极低，原代码也有类似问题。
2. **字符串 replace 非路径精确替换**：`agentList[i].workspace.replace(currentDirName, expectedDirName)` 仍是字符串 replace（认领卡 E 提到要用 path 精确替换，未改）。如果 workspace 路径中 `currentDirName` 出现多次会全部替换——概率极低但不严谨。

**实际影响**：核心原子性问题已解决，这两个是边界遗留，当前不修。

### N-4 P0-1 历史消息 dataUrl 无 path 时图片丢失

**位置**：`web/js/components/message-builder.js:108-117`

`buildMultimodalContent` 删除了 dataUrl 分支后，只检查 `att.path`。若历史会话中有 `att.dataUrl` 但无 `att.path` 的消息（极旧数据），重发该轮时图片不会发送。

**实际影响**：仅在"重发含极旧图片附件的历史消息"时触发，概率低；存储视图仍保留 dataUrl（历史数据未动），仅发送视图丢失。可接受。
