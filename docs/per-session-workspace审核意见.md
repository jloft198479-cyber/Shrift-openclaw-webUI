## 二、方案评估：报告低估了方案 A 的三个风险

报告推荐方案 A，方向正确。但方案 A 的"限制"一节（报告 L205-208）把三个实质性问题一笔带过，实际严重性更高。

### 🟡 风险 1：自动切换全局 workspace 的污染面大于"多 tab"

**报告原文**（L207）："切换 session 时如果自动切换全局 workspace，会影响并发场景（多个 tab/窗口同时操作）"

**补充**：不止多 tab。单 tab 内就有一个高频场景——**dispatch 模式下会话 A 正在等待子 Agent 回传，用户切到会话 B**。此时自动切换全局 workspace 会触发 `syncProjectContext` 重写主 Agent 的 AGENTS.md，而会话 A 的子 Agent 可能还在用旧的 AGENTS.md 上下文工作。

更深层的问题是：**全局 workspace 是共享可变状态，per-session 切换在向这个共享状态写入**。这违反"真理源自一处"——workspace 的"真理"在 session 层（每个会话有自己的），但物理存储还在全局层。自动切换 = 让全局层不停追赶 session 层，追赶过程中任何并发的读（Gateway 创建新会话、子 Agent spawn）都可能读到过渡态。

**这与刚修复的 P0-2（切换不清理 dispatching）是同一类问题的延伸**：切换会话时不仅有"清理"动作，方案 A 还要新增"写入"动作，状态机更复杂了。

### 🟡 风险 2："消息注入兜底"与已确立的原则冲突

**报告原文**（L196）："当检测到 session.workspace ≠ 当前全局 workspace 时，在首条用户消息前注入一条上下文提示"

**补充**：这个兜底实现起来很 awkward，且与两条已确立的原则冲突：

1. **与 P0-1 token 控制冲突**：刚做的 dataUrl 剥离就是为了控制 token。如果续聊时每次都注入项目路径提示（哪怕是首条），长会话里这条提示会被 ContextPruning 保留（它是 system-like 内容），持续占用 token。如果只注入首条，后续轮次 Agent 又会"忘记"项目切换。

2. **与"绝不硬编码"原则冲突**（architecture.md L54-58）：注入的项目路径本质上是从 session.workspace 派生的动态内容，但它被塞进了消息体而非配置层。这不算严格意义的硬编码，但属于"动态内容绕过了配置注入机制"——和 tech-rules.md 踩坑 #10（硬编码技能命令）是同一类病根。

**实质**：Gateway 在会话创建时把 AGENTS.md 固化进 system prompt，这是 Gateway 的设计。方案 A 试图绕过这个固化，但绕不过去——旧会话的 system prompt 已经固化了。消息注入不是"兜底"，是"补丁"，而且是个会腐烂的补丁。

### 💭 风险 3：切换=写入，与"切换=清理"的心智模型冲突

**补充**：product-context.md 第 32 行和刚修复的 P0-2 确立了"会话切换前统一清理（_beforeSwitch）"的模式。切换是一个**轻量、可逆、无副作用**的操作。方案 A 让切换触发"写全局配置 + 写 AGENTS.md 文件"，把切换变成了一个**有副作用的重操作**。

这不是不能做，但需要明确：**方案 A 改变了"切换会话"的语义**。这个改变应该在产品层面被 consciously 接受，而不是作为"限制"悄悄滑过去。

## 三、被忽略的架构视角：上下文固化的责任边界

报告聚焦在"怎么让 session 携带 workspace"，但有一个更上游的问题没问：**项目上下文应该在哪个层固化？**

当前设计：Gateway 在**会话创建时**读 AGENTS.md → 固化进 system prompt → 会话生命周期内不可变。

这个设计意味着：
- **新会话**：方案 A 能解决（创建前把 AGENTS.md 写对）
- **旧会话续聊**：方案 A 解决不了（system prompt 已固化），只能靠补丁
- **会话中途切项目**：任何方案都解决不了（除非改 Gateway 支持 per-request workspace）

所以方案 A 的**真实价值边界**是：**让新会话绑定正确的项目上下文，并在切换历史会话时给用户一个明确的"项目不匹配"提示**。它不应该试图解决"旧会话续聊的上下文正确性"——那个场景靠提示用户"切项目后请新开会话"比靠消息注入补丁更诚实。

## 四、修正后的建议

报告的结论"优先评估方案 A"是对的，但方案 A 的实施范围应该收窄。建议如下：

### 做的部分（方案 A 核心，低风险高价值）

1. **数据层**：`ensureSession` 快照 `State.workspace.path` 写入 `session.workspace`。✅ 报告方案 A 第 1 点，无争议。
2. **会话列表展示**：`getSessionList` 返回 workspace 字段，前端列表项显示项目名。✅ 报告方案 A 第 5 点，纯展示，无风险。
3. **新建会话**：创建前确保 workspace 已写入 repoRoot + AGENTS.md 已同步。✅ 报告方案 A 第 2 点，但需补一个时序保证——`PUT /api/workspace` 返回成功后才允许 `sendMessage`。

### 不做或谨慎做的部分（方案 A 的高风险点）

4. **切换历史会话自动切换全局 workspace** — 🟡 建议改为**提示而非自动切换**。
   - 理由：自动切换有并发污染风险（风险 1），且改变了切换语义（风险 3）。
   - 替代方案：切换到历史会话时，若 `session.workspace ≠ 当前全局 workspace`，在 UI 顶部显示一个非阻塞提示条："该会话属于项目 X，当前项目是 Y，[切换到 X] / [忽略]"。用户主动点才切换，避免自动副作用。
   - 这与 architecture.md 的"退化安全"原则一致：不替用户做决定，但给出明确提示和恢复建议。

5. **旧会话续聊的消息注入兜底** — 🟡 建议不做，改为 UI 引导。
   - 理由：与 token 控制和硬编码原则冲突（风险 2），且是会腐烂的补丁。
   - 替代方案：检测到续聊时 workspace 不匹配，在输入框上方显示提示"当前项目与该会话不同，建议新开会话以获得完整上下文"。把决定权交给用户，而不是悄悄注入消息。
   - 这比消息注入更诚实——用户知道上下文可能不完整，可以选择新开会话。

### 留给未来的部分

6. **方案 B（改 Gateway）作为长期路径** — 报告判断"方案 A 可作为方案 B 的前置准备"是准确的。数据层（session 携带 workspace）一旦建立，未来 Gateway 开放 per-request header 时，只需 proxy.js 加一行转发，零数据层改动。这个演进路径是干净的。

---

## 五、一句话总结

报告的事实调查扎实、方案对比逻辑清晰，结论方向正确。但方案 A 的实施范围应该收窄：**只做"新会话绑定 + 列表展示 + 不匹配提示"，不做"自动切换全局 workspace"和"消息注入兜底"**。前者是低风险高价值，后者是高风险低价值且与已确立的架构原则冲突。把"旧会话续聊"的场景交给 UI 引导而非代码补丁，把真正的 per-request workspace 留给未来的方案 B。
